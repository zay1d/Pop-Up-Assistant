## Денежная модель (актуальная — вариант коллеги)

Стоимости задаёт менеджер **вручную** (три поля на размещении); ставка зоны
`dayRate` используется только как запасной вариант для старых записей.

| Поле записи | Смысл | Ввод |
|---|---|---|
| `baseCost` | Начальная стоимость (до скидки) | вручную (`#f-base`) |
| `agreedCost` | Согласованная стоимость = **итог к оплате** | вручную (`#f-agreed`) |
| `monthlyCost` | Стоимость в месяц | **только вручную** (`#f-monthly`); пусто ⇒ показывается «—», авто-расчёта нет |

- **Скидка вычисляется:** `(base − agreed) / base × 100`.
- **Совместимость со старыми записями:** если `agreedCost` не задана, `placementMoney()`
  берёт прежнюю модель — `manualCost` (ручная сумма, без скидки) либо расчёт из
  ставки зоны `dayRate × дни × (1 − скидка%)`. Поэтому данные, введённые до перехода,
  не ломаются.
- **Распределение по времени — ПО ДНЯМ** (`perDay = agreedCost ÷ дни`): дашборд
  «Поступления по месяцам», накопительный прогноз, мешки и помесячные колонки в
  «Сводке» считают по фактическим дням месяца.
- **Сводка для руководства:** колонки «В месяц / Начальная / Согласованная / Скидка»
  + помесячная разбивка, закреплённые левые колонки, строка «Итого», фильтр по
  статусам («Отказано» в итоги не входит).

> Историческая справка: ранее была реализована модель «помесячного начисления
> поровну» (`monthlyAccrual`/`placementMonthSpan`, «в месяц = итог ÷ число месяцев»).
> По решению владельца она **заменена** на модель коллеги выше (день-based). Полей
> `manualMonth`/`monthlyAccrual` в текущем `app.js` нет.

## Рабочий процесс обновлений от команды

`app.js`/`data.js`/`styles.css` разрабатывает команда/коллега локально и присылает
zip (`popupdeploy…`). Порядок наложения на репозиторий (источник правды — git/Pages):

1. Скопировать из архива **только** `app.js`, `styles.css` (и `data.js`, если менялся).
2. **НЕ брать** их `index.html` — он локальный (без облака); в репозитории живёт
   облачный `index.html` (`APP_API_BASE` + `cloud.js`).
3. **Не трогать** `cloud.js`, `server/`, `face.png` — их нет в архивах команды.
4. Проверить совместимость с облаком: `DB_VER` и форма дампа (`{app,version,currency,
   zones,placements,history,labels,activities,files}`) должны остаться прежними; глобали
   ядра (`State`, `dbGetAll/Put/Del`, `loadAll`, `toast`, `go`, `_db`, `exportData`) — на месте.
5. `node --check app.js && node --check cloud.js`, коммит, пуш в ветку деплоя.

> Данные (арендаторы, документы) живут на сервере + R2, а не в коде — деплой кода их
> не трогает. Фиксы облачного слоя (защита `URL.createObjectURL` от пустых blob'ов,
> нормализация `start/end`) живут в `cloud.js`, поэтому переживают обновления `app.js`.

## Частые операции

- **Сменить адрес API у фронта**: правка `window.APP_API_BASE` в `index.html`
  → коммит/пуш → Pages пересоберётся.
- **Деплой изменения фронта**: просто пуш в ветку деплоя; Actions пересоберёт.
- **Полная очистка данных**:
  `psql "$DATABASE_URL" -c "UPDATE workspace SET state='{}'::jsonb WHERE id=1; TRUNCATE documents;"`
  (объекты в R2 при этом «осиротеют» — чистятся отдельно).

## Известные ограничения / будущее

- **Нет авторизации** — любой с адресом API может менять данные. Если понадобится
  защита: добавить общий пароль (заголовок/JWT) — точки для этого: `Api.req` в
  `cloud.js` и middleware на сервере.
- **«Осиротевшие» файлы в R2**: при удалении документа через карточку blob
  удаляется из IndexedDB, но объект в R2 удаляется только если фронт вызовет
  `DELETE /api/documents/:id`. Файлы, убранные при редактировании размещения,
  могут остаться в R2. Возможное улучшение — серверная сборка мусора (diff
  ключей в `workspace.state` против таблицы `documents`).
- **Загрузка тянет все документы** при входе (чтобы не менять app.js, который
  читает blob'ы из IndexedDB). Для больших архивов — будущая оптимизация:
  ленивое скачивание по требованию (потребует точечной правки рендера в app.js).
- **Одновременное редактирование**: модель «один редактор». PUT заменяет весь
  датасет — при двух одновременных редакторах побеждает последний сохранивший.
